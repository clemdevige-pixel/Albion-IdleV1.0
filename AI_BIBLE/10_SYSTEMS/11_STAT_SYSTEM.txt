## ALBION IDLE — STAT SYSTEM

**Document type:** System Specification
**Status:** ACTIVE — aligned with current runtime
**Authority:** `000_PROJECT_BIBLE.txt` + live gameplay/data implementation

---

# Purpose

The Stat System defines the stable combat values used by the Hero and equipment. It calculates/aggregates values; CombatRuntime decides how those values resolve in combat.

The system must remain deterministic, readable and data-driven.

---

# Current Combat Stat Model

The current combat model uses these principal values:

- Maximum Health;
- physical/magical offensive values supplied by weapons/abilities;
- Armor;
- Magic Resistance;
- Attack Speed where defined by the combat/weapon profile.

There is no Energy/Mana resource in the current combat design.

Critical-hit systems are not part of the current validated combat baseline.

The canonical naked Hero defensive baseline used by the current runtime benchmarks is:

```text
Maximum Health: 300
Armor: 0
Magic Resistance: 0
```

These are balancing values and must stay synchronized with authoritative runtime/data configuration.

---

# Stat Sources

Final combat values may be affected by:

- Hero baseline;
- equipped weapon;
- armor equipment;
- offhand;
- mastery;
- enchantment;
- active gameplay effects/consumables where their owning system applies them.

The Stat System must not invent a second implementation of those systems.

---

# Equipment

Equipment is a major source of combat power.

Armor pieces can contribute Maximum Health, Armor and Magic Resistance according to their authored data.

Weapons own their offensive profile and ability package.

One-handed weapons may equip an offhand. Offhand bonuses belong to the offhand and must remain separable from the intrinsic weapon profile for balancing purposes.

This distinction is mandatory because multiple offhand identities are expected.

---

# Enchantment

Enchantments are multiplicative equipment upgrades according to the current equipment/enchantment implementation.

Benchmark calculations must use the same enchantment rules as gameplay. Do not document or implement an independent approximation when the shared gameplay rule is available.

Equipment not eligible for a given enchantment rule must not be silently upgraded by benchmark helpers.

---

# Mastery

Mastery contributes permanent specialization according to authored mastery data.

The Stat System consumes the resulting values. It does not own mastery progression or unlock logic.

Benchmark scenarios must specify the mastery level expected at the progression checkpoint being tested.

---

# Health

Current Health is mutable runtime state.

Maximum Health is derived from the current character/loadout state.

The invariant is:

```text
0 <= Current Health <= Maximum Health
```

A defeated Hero remains at zero until a system explicitly revives/heals them. Recalculating stats must not itself revive the Hero.

When equipment changes Maximum Health during normal live character management, the owning character/stat flow must preserve a coherent health state and never grant unintended free healing.

---

# Armor and Magic Resistance

Armor and Magic Resistance are separate defensive axes.

They must not be collapsed into one generic `Defense` value in balancing documentation or benchmark output.

For cross-build diagnostic comparison, tooling may calculate effective-health metrics such as:

- physical EHP;
- magical EHP;
- average EHP.

These are benchmark/analysis metrics, not additional stored Hero stats.

---

# Offensive Analysis

Raw weapon damage alone is not sufficient to describe offensive power.

Balance tooling may derive:

- auto-attack DPS;
- ability DPS;
- sustained DPS;
- opener DPS over defined windows;
- ability unlock contribution.

These values are diagnostic metrics derived from the real weapon/ability data.

---

# Weapon vs Loadout Power

Balancing must distinguish:

```text
Weapon-only profile
```

from:

```text
Weapon + armor + optional offhand loadout
```

A shield's EHP must not be attributed to the Broadsword itself. Likewise, future offensive or utility offhands must be evaluated as explicit loadout components.

The reusable package benchmark is responsible for exposing both views.

---

# Data Ownership

Stat numbers must be authored in the appropriate data/configuration source.

UI components, scenes and benchmark tests must consume authoritative values rather than hardcoding alternative balancing copies.

When a benchmark needs a baseline, that baseline must be kept in parity with the live runtime and protected by tests.

---

# Determinism

Given identical:

- Hero baseline;
- equipment;
- enchantment;
- mastery;
- active effects;

the Stat System must produce identical combat values.

Results must not depend on frame rate, UI state, wall-clock time or random iteration order.

---

# Balancing Validation

The current reusable tools are:

- `apps/client/src/runtime/CombatRuntimeBenchmarkHarness.ts` for exact live-runtime encounters;
- `apps/client/src/data/weaponIdealBenchmark.ts` for weapon/defensive analytical profiles;
- `apps/client/src/data/weaponPackageBenchmark.ts` for weapon-only, neutral and explicit-loadout scoring.

Synthetic metrics diagnose *why* a build behaves differently. Live CombatRuntime tests determine whether a progression checkpoint actually clears.

---

# Required Regression Properties

Tests should protect at minimum:

- naked Hero baseline parity;
- full-equipment aggregation;
- Armor/MR separation;
- one-handed offhand contribution;
- enchantment scaling parity;
- mastery scaling parity;
- weapon-only vs loadout separation;
- deterministic repeated calculations;
- health invariants;
- exact runtime benchmark compatibility.

---

# Out of Scope

This document does not own:

- enemy curve authoring;
- ability behavior;
- potion behavior;
- mastery progression rules;
- equipment recipes;
- zone progression requirements;
- loot/reward balance.

Those systems consume or modify stats through their dedicated implementation/data.

---

# Summary

The current Albion Idle stat model is intentionally compact but no longer the old `HP / Damage / generic Defense` prototype. Combat balancing uses real Maximum Health, Armor, Magic Resistance and weapon/ability offensive profiles, with enchantment, mastery and offhands treated as explicit power sources.

The naked Hero baseline is 300 HP / 0 Armor / 0 MR, and all balance tooling must remain in parity with the live runtime.
