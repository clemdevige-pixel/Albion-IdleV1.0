# 37. SAVE SYSTEM

## Purpose

The Save System is responsible for persisting every piece of player progression.

It guarantees that all permanent progress survives:

- Game restart
- Client crash
- Network interruption
- Device change
- Server restart
- Game updates

The Save System is fully server-authoritative.

---

# Design Goals

The Save System must:

- Prevent data loss.
- Prevent duplication exploits.
- Prevent rollback exploits.
- Support future multiplayer features.
- Support future player economy.
- Allow version migrations.
- Be deterministic.
- Be scalable.
- Be independent from gameplay systems.
- Restore the exact player state.

---

# Core Philosophy

The server is the only source of truth.

The client never owns progression.

The client only displays cached information while the server validates every permanent modification.

---

# Architecture

The Save System consists of two layers:

## Local Cache

Stored on the player's device.

Purpose:

- Faster loading
- UI responsiveness
- Temporary cache
- Session recovery

The local cache is never authoritative.

---

## Server Save

Stored in the backend database.

Contains the complete player state.

Every permanent action modifies this save.

If local and server data differ:

The server always wins.

---

# Server Authority

The server owns:

- Character progression
- Equipment
- Inventory
- Silver
- Resources
- Masteries
- Workers
- Island
- Crafting
- Refining
- Loot
- Combat results
- Unlocks
- Statistics

The client cannot permanently modify any of these values.

---

# Online Requirement

The game is Online Only.

A connection is required for gameplay.

Offline progression is not supported.

Reasons:

- Prevent cheating
- Protect economy
- Protect future player trading
- Protect future market
- Simplify synchronization
- Simplify authoritative validation

# Save Triggers

The server saves after every important progression event.

Examples include:

- Combat completed
- Loot received
- Equipment changed
- Craft completed
- Refining completed
- Gathering completed
- Worker task completed
- Vendor transaction
- Silver modified
- Mastery increased
- Island upgraded
- Unlock obtained
- Settings changed (when persistent)

---

# Autosave

In addition to event-driven saves:

The server performs automatic saves periodically.

Recommended interval:

60 seconds

Autosave acts as a safety layer.

---

# Final Save

When the player disconnects:

1. Active actions finish safely.
2. Pending transactions complete.
3. Final snapshot is created.
4. Save is committed.
5. Session closes.

---

# Snapshot Philosophy

The Save System uses complete snapshots.

Each save contains the full player state.

No previous save is required to restore progression.

Each snapshot is completely independent.

---

# Snapshot Advantages

Complete snapshots provide:

- Simple restoration
- Robust recovery
- Easier debugging
- Easier migrations
- Lower corruption risk
- Predictable loading

Storage cost is acceptable for an RPG.

# Save Frequency

Important actions trigger immediate saves.

Minor runtime values may wait for autosave.

This balances reliability and server load.

---

# Atomic Saves

Every save operation is atomic.

Either:

Entire snapshot succeeds

or

Nothing changes.

Partial saves are never accepted.

---

# Transaction Ordering

All gameplay events execute before saving.

Example:

Loot

↓

Inventory Updated

↓

Silver Updated

↓

Save Snapshot

Never:

Save

↓

Loot

This prevents inconsistent states.

---

# Save Queue

Incoming save requests enter a queue.

If multiple save requests occur rapidly:

They are merged whenever possible.

Only the newest valid state is written.

---

# Save Priority

Priority order:

Critical

↓

High

↓

Normal

Critical saves include:

- Purchases
- Loot
- Currency
- Inventory
- Equipment

---

# Save Lock

While a save is executing:

Player data is locked.

No concurrent save may modify the same snapshot.

This prevents race conditions.

---

# Duplicate Protection

Every save request receives:

SaveTransactionID

Duplicate requests are ignored.

---

# Crash Recovery

If the server crashes:

The latest completed snapshot is restored.

Incomplete saves are discarded.

---

# Integrity Verification

Each snapshot includes:

Checksum

During loading:

Checksum is verified.

Invalid snapshots are rejected.

---

# Save Validation

Before saving:

The server validates:

- Item ownership
- Inventory consistency
- Currency consistency
- Equipment validity
- Progression validity

Invalid states are rejected.

# Migration Safety

Migration must be:

- Deterministic
- Idempotent
- Logged
- Tested

A migration may never corrupt player progression.

---

# Failed Migration

If migration fails:

Loading stops.

The snapshot remains unchanged.

Support logs receive detailed diagnostics.

---

# Backward Compatibility

The Save System supports loading previous save versions through migrations.

Direct loading of outdated snapshots is not required.

---

# Forward Compatibility

Old clients must never overwrite newer save versions.

Server validation prevents downgrade corruption.

---

# Save Compression

Snapshots may be compressed before storage.

Compression must not modify data.

---

# Encryption

Server saves may be encrypted at rest.

Sensitive information should never be stored in plain text where avoidable.

---

# Local Cache

- Recently loaded snapshot

# Summary

The Save System is fully server-authoritative and uses complete snapshot persistence.

Gameplay is online-only, with the server acting as the single source of truth. The client stores only a local cache for faster loading and improved responsiveness.

Progress is saved immediately after every important gameplay event and reinforced by periodic autosaves. Every snapshot is self-contained, versioned, validated, and protected by checksums and atomic transactions.

Automatic migration ensures long-term compatibility across game updates, while modular serialization keeps the system scalable and maintainable.

This architecture provides a secure, reliable foundation for future multiplayer features, the player-driven economy, and long-term live service development.
