# 21. STAT DATA

---

# Purpose

Stat Data defines the shared identifiers and metadata for gameplay statistics. Runtime values and balancing numbers remain owned by their appropriate gameplay/data systems.

The document must describe statistics that actually exist or are explicitly authored. It must not turn speculative future RPG stats into Version 1 requirements.

---

# Principles

## Explicit
Every runtime statistic must have a stable meaning and identifier.

## Shared
Character, equipment, abilities, effects, UI and balance tooling must consume the same concepts rather than maintaining incompatible copies.

## Data-driven
Balancing values belong in data/configuration rather than UI or scene conditionals.

## Deterministic
Identical inputs produce identical values.

## Extensible
New statistics may be added when a validated gameplay feature requires them. They are not pre-created merely for hypothetical future systems.

---

# Current Combat Statistical Vocabulary

The current validated combat model requires at minimum concepts for:

- Maximum Health;
- Armor;
- Magic Resistance;
- weapon physical/magical damage as required by weapon/ability data;
- Attack Speed where required by the weapon/combat profile.

There is no Energy/Mana statistic in the current combat design.

Critical Chance, Critical Damage, Dodge, Block, Cooldown Reduction and similar RPG stats are not part of the current validated baseline unless separately introduced by an implemented/validated system.

---

# Hero Defensive Baseline

Current naked Hero benchmark baseline:

```text
Maximum Health = 300
Armor = 0
Magic Resistance = 0
```

This is a balancing baseline, not a reason to duplicate the numbers across multiple runtime systems. The authoritative implementation and benchmark parity tests must remain synchronized.

---

# Definition Metadata

Where the data architecture represents a stat as a reusable definition, useful metadata may include:

```text
id
name/category
value type
minimum/maximum when applicable
precision/display format
visibility
```

Only metadata actually required by consuming systems should be added. Avoid speculative generic-stat infrastructure.

---

# Runtime Values

Definitions and runtime values are separate concepts.

Examples of runtime values:

- current/max health;
- current Armor/MR after equipment aggregation;
- weapon damage profile;
- temporary effect state owned by an effect/consumable system.

Current Health is runtime state and must remain between zero and Maximum Health.

---

# Equipment and Offhands

Equipment bonuses are authored on the equipment/content data that owns them.

One-handed weapons and offhands are independent power sources. A benchmark or UI comparison must not merge a specific shield permanently into the weapon's intrinsic stat definition.

Future offhands may be defensive, offensive, utility or hybrid without requiring a redesign of the weapon stat model.

---

# Enchantment and Mastery

Enchantments and masteries modify power according to their dedicated gameplay/data rules.

Stat Data does not duplicate those formulas.

Consumers, including benchmark tools, must use the shared implementation wherever possible.

---

# Derived Balance Metrics

The following are analysis metrics and do not need to become stored gameplay stats:

- sustained DPS;
- opener DPS;
- physical EHP;
- magical EHP;
- average EHP;
- offense index;
- defense index;
- loadout/package score.

They exist to compare builds and diagnose balance behavior.

---

# Validation

Stat-related validation should catch relevant failures such as:

- invalid/unknown stat references;
- invalid numeric values;
- negative Armor/MR when not explicitly supported;
- Maximum Health below its permitted minimum;
- Current Health above Maximum Health;
- duplicated equipment contribution;
- benchmark baselines diverging from live runtime values.

---

# Balancing Sources

Combat progression curves:

`packages/data/src/config/combat-progression.ts`

Analytical weapon benchmark:

`apps/client/src/data/weaponIdealBenchmark.ts`

Reusable weapon/loadout scoring:

`apps/client/src/data/weaponPackageBenchmark.ts`

Exact runtime progression validation:

`apps/client/src/runtime/CombatRuntimeBenchmarkHarness.ts`

Stat Data must not replace these sources with copied balancing tables.

---

# Acceptance Rules

- No Energy/Mana is introduced accidentally.
- Armor and Magic Resistance remain distinct.
- Offhand contribution remains independently measurable.
- New statistics require a concrete gameplay consumer.
- Balance metrics are derived rather than persisted as duplicate gameplay truth.
- Runtime and benchmark baselines remain synchronized through tests.

---

# Summary

Stat Data provides a stable shared language for the statistics Albion Idle actually uses. It intentionally avoids the old speculative universal-stat catalog. New stats are added because gameplay needs them, while combat balance remains grounded in authoritative equipment/ability data and exact CombatRuntime validation.
