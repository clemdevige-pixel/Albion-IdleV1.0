# 26. STATUS EFFECT DATA

---

# Purpose

The Status Effect Data document defines every persistent gameplay effect that can temporarily modify an entity.

Unlike Effects, which execute instantly, Status Effects persist for a duration and continuously influence gameplay.

Examples include:

- Bleeding
- Poison
- Burning
- Stun
- Root
- Slow
- Haste
- Regeneration
- Shield
- Damage Amplification

Status Effects are entirely data-driven.

---

# Design Philosophy

The Status Effect system follows six core principles.

---

## Persistent

A Status Effect exists over time.

Unlike an Effect, it is updated every simulation tick until it expires or is removed.

---

## Modular

Status Effects never contain gameplay logic directly.

Instead, they are composed of reusable Effect definitions.

Example:

```
Bleeding

↓

Tick Damage Effect

↓

Visual Effect

↓

Expiration
```

---

## Reusable

One Status Effect may be applied by many different Abilities.

Example:

```
Bleeding

↓

Sword

↓

Axe

↓

Boss Attack

↓

Trap
```

---

## Deterministic

Status Effects always produce identical results given identical conditions.

No hidden randomness exists.

---

## Runtime Independent

Definitions remain immutable.

Runtime instances store:

- Remaining Duration
- Remaining Stacks
- Owner
- Source

---

## Extensible

Future Status Effects can be created without adding gameplay code.

---

# Responsibilities

Status Effect Data defines:

- Identity
- Category
- Duration
- Stack Rules
- Refresh Rules
- Tick Frequency
- Applied Effects
- Removal Rules
- Immunities
- Visual References

Status Effect Data does NOT define:

- Ability Cooldowns
- Damage Formulas
- Character Statistics

Periodic Status Effects reference one Effect executed every tick.

Example:


# Stack Behavior

Supported stacking rules:

---

## Replace

Newest replaces oldest.

---

## Refresh Duration

Duration resets.

Stack count remains unchanged.

---

## Add Stack

Stack count increases.

---

## Independent

Each application creates an independent instance.

---

## Ignore

Additional applications are ignored.

---

# Refresh Rules

When reapplied:

Supported options:

```

Refresh Effects

Increase Stacks

Ignore

Replace
```

# Expiration Rules

Status Effects expire when:

- Duration reaches zero
- Explicitly removed
- Owner dies
- Cleansed
- Purged

Infinite effects require explicit removal.

# Validation

Validation checks:

- Unique ID
- Valid Category
- Valid Duration
- Valid Tick Rate
- Existing Effect References
- Existing VFX
- Existing Audio
- Valid Stack Rules
- Valid Refresh Rules
- Valid Maximum Stacks

Invalid definitions never load.

---

# Unsupported Features

Version 1 does not support:

- Scripted Status Effects
- Runtime-generated Status Effects
- Dynamic Categories
- Conditional Stack Rules
- Formula-based Durations

# Acceptance Criteria

The Status Effect Data document is complete when:

- Every Status Effect has a unique identifier.
- Categories are predefined.
- Durations are configurable.
- Tick rates are configurable.
- Stack behavior is configurable.
- Refresh rules are configurable.
- Effects are referenced by ID.
- Immunities are supported.
- Runtime instances remain separate from definitions.
- Validation guarantees data integrity.

---

# Immutable Design Rules

Rule 01

Every Status Effect is completely data-driven.

Rule 02

Every Status Effect has a globally unique identifier.

Rule 03

Status Effects persist independently from Abilities.

Rule 04

Gameplay logic is delegated to reusable Effects.

Rule 05

Stack behavior is explicit.

Rule 06

Refresh behavior is explicit.

Rule 07

Tick execution is deterministic.

Rule 08

Definitions never contain runtime state.

Rule 09

Validation prevents invalid definitions.

Rule 10

Status Effects may define immunity tags.

Rule 11

Exclusive groups prevent incompatible effects from coexisting.

Rule 12

Visual and audio references are data-driven.

Rule 13

Runtime instances are immutable definitions plus temporary state.

Rule 14

Every Status Effect may declare its content source.

Rule 15

Future Status Effects must remain compatible with the shared data architecture.

---

# Summary

The Status Effect Data document defines every persistent gameplay modifier through a modular, reusable and fully data-driven architecture. By separating long-lived effects from instant Effects and Abilities, it enables deterministic combat, flexible stacking rules, reusable gameplay behaviors and scalable content creation. This architecture supports hundreds of buffs, debuffs and crowd control effects while remaining easy to balance, validate and extend.
