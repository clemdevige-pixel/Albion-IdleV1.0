# 27. ENEMY DATA

---

# Purpose

Enemy Data defines enemy identity/content while shared combat progression data determines how encounters scale through world bands, zones and segments.

Enemy definitions describe what an enemy is. They do not implement CombatRuntime or duplicate world difficulty curves.

---

# Enemy Definition Responsibilities

Enemy/content data may define or reference:

- stable ID;
- display identity;
- family/category;
- base combat profile;
- abilities/AI profile;
- loot/rewards;
- spawn/encounter metadata;
- visual/audio references;
- tags/content source.

Runtime state such as current HP, cooldowns, target and effects remains outside immutable content definitions.

---

# Data-Driven Rule

Adding a conventional enemy must not require a new combat code path.

New code is justified only when the enemy introduces a genuinely new mechanic that cannot be represented by existing reusable systems.

Enemy identity, zone difficulty and combat simulation must remain separate concerns.

---

# World Difficulty Scaling

The current world progression model does NOT use the obsolete infinite Cycle scaling model.

World difficulty is authored by world band and zone through shared combat progression configuration:

`packages/data/src/config/combat-progression.ts`

A zone curve provides authored start/end multipliers for relevant enemy combat dimensions. Segment interpolation and encounter growth then produce the actual progression inside the zone.

Therefore enemy power in a progression encounter is conceptually:

```text
Enemy/content base profile
× authored world/zone combat curve
× segment position
× encounter growth / encounter-specific rules
```

The exact implementation remains authoritative over this conceptual description.

---

# Zone Purpose Before Numbers

Enemy difficulty values must be tuned against an explicit progression contract.

For the validated Blue world:

- Forest teaches and should not create meaningful starter friction;
- early Swamp creates the first starter wall;
- Swamp rewards progressive T3 crafting;
- Highlands transitions T3 → T4;
- Steppe consolidates T4.0 and introduces enchantment pressure;
- Frostpeak transitions T4.1 → T4.2, with T4.3 as the reliable S10 AFK threshold.

Future world bands must define an equivalent intended equipment envelope before numerical enemy tuning.

---

# Runtime Validation

Enemy balance is accepted through the exact live CombatRuntime, not by comparing isolated enemy stat totals.

Reusable harness:

`apps/client/src/runtime/CombatRuntimeBenchmarkHarness.ts`

A benchmark scenario supplies:

- zone;
- segment;
- weapon;
- equipment/loadout;
- mastery;
- enchantment;
- potion policy.

The output measures actual clear/failure behavior and remaining HP.

---

# Weapon Diversity Constraint

Enemy curves must be tested against multiple representative weapon profiles.

A zone must not be tuned exclusively around one weapon.

Comparable weapons may legitimately differ by roughly 5-10% where their combat identities justify it. Larger runtime differences should first be diagnosed through weapon/package benchmarking before weakening or strengthening the entire enemy curve.

This prevents a weapon-specific issue from being hidden inside global monster balance.

---

# Defensive and Offensive Pressure

Enemy tuning must account for both:

- player offensive package / time-to-kill;
- player defensive package / effective survivability.

One-handed weapons with offhands require explicit loadout evaluation. Shield survivability belongs to the shield/loadout, not intrinsically to the weapon.

---

# Consumables and AFK Thresholds

Potion-assisted progression and reliable AFK progression are distinct balance states.

An enemy/zone checkpoint may intentionally:

- block an unprepared AFK build;
- become clearable with potion assistance;
- become reliably AFK-clearable after the next intended equipment/enchantment upgrade.

Frostpeak S10 is the current reference example: T4.2 is an assisted/optimized push state; T4.3 is the reliable AFK target.

---

# Validation

Enemy/content definitions should validate all references they actually own, including IDs, abilities, loot and assets where applicable.

Combat balance regression must separately validate that authored enemy/zone values still satisfy the progression contract after changes to:

- weapon data;
- armor/offhands;
- abilities;
- enchantment;
- mastery;
- combat formulas;
- zone curves.

---

# Extensibility

Future enemies, families and world bands should reuse:

- existing enemy/content schemas;
- shared combat progression configuration;
- exact CombatRuntime benchmark harness;
- weapon/package benchmark tooling.

Do not create parallel per-band combat simulators or copied balancing tables.

---

# Summary

Enemy Data owns enemy identity and reusable content references. World/zone progression data owns difficulty curves. CombatRuntime owns actual resolution. Keeping those responsibilities separate makes future zones and enemies data-driven and allows every new progression chapter to be calibrated with the same benchmark pipeline already validated on Blue.
