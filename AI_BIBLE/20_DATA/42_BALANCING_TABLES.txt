# 42. BALANCING TABLES

---

# Purpose

The Balancing Tables document defines every numerical progression table used by the game.

Balancing Tables centralize progression values and mathematical curves outside gameplay systems.

Instead of hardcoding numbers into systems, every scalable value references one or more balancing tables.

Examples include:

- Experience Requirements
- Health Scaling
- Damage Scaling
- Reward Scaling
- Cycle Multipliers
- Crafting Time
- Gathering Speed
- Repair Cost
- Economy Values

Balancing Tables are shared across the entire project.

---

# Design Philosophy

The Balancing Table system follows seven principles.

---

## Single Source of Truth

Every scalable value exists in exactly one table.

Gameplay systems never duplicate progression values.

---

## Fully Data Driven

Every balancing value is stored externally.

Changing progression never requires modifying gameplay code.

---

## Shared

Multiple systems may reference the same table.

Example:

```
Standard XP Table

↓

Sword Mastery

↓

Bow Mastery

↓

Axe Mastery
```

---

## Deterministic

Tables contain predefined values only.

No balancing table generates runtime randomness.

---

## Modular

Each table represents one balancing concern.

Examples:

- XP
- Damage
- Health
- Rewards

They remain completely independent.

---

## Easy To Tune

Designers should be able to rebalance the game by editing tables without touching gameplay logic.

---

## Extensible

New balancing tables may be introduced at any time without impacting existing systems.

---

# Responsibilities

Balancing Tables define:

- Numerical Progression
- Multipliers
- Curves
- Lookup Values
- Shared Progression Data

Balancing Tables do NOT define:

- Gameplay Logic
- Runtime State
- Character Statistics
- Enemy Definitions
- Item Definitions

---

# Table Definition

Every Balancing Table contains:

```text
ID

↓

Table Type

↓

Lookup Values

↓

Interpolation Mode

↓

Tags
```

---

# Identifier

Every Balancing Table owns one globally unique identifier.

Examples:

```
xp_table_mastery_standard

health_scaling_cycle

reward_scaling_zone

repair_cost_table

crafting_time_table
```

---

# Table Types

Version 1 supports:

- Experience
- Scaling
- Multiplier
- Cost
- Duration
- Probability

Future versions may introduce additional categories.

---

# Lookup Method

Tables are accessed using keys.

Examples:

```
Level

↓

Experience
```

or

```
Cycle

↓

Multiplier
```

or

```
Tier

↓

Repair Cost
```

Gameplay systems never calculate values internally.

---

# Table Format

Every table follows the same structure.

Example:

```json
{
    "id": "xp_table_mastery_standard",
    "type": "Experience",
    "entries": [
        {
            "key": 1,
            "value": 100
        },
        {
            "key": 2,
            "value": 250
        },
        {
            "key": 3,
            "value": 450
        }
    ]
}
```

---

# Interpolation

Version 1 supports two lookup modes.

---

## Exact Lookup

The requested key must exist.

Example:

```
Tier 4

↓

120 Silver
```

---

## Continuous Lookup

Values may be interpolated.

Example:

```
Cycle 5

↓

1.35

Cycle 6

↓

1.42
```

Interpolation method:

```
Linear
```

---

# Experience Tables

Shared by Masteries.

Example:

```
Mastery

↓

XP Table

↓

XP Requirement
```

---

# Scaling Tables

Used by:

- Enemy Health
- Enemy Damage
- Reward Multipliers
- Cycle Scaling

These tables work together with the Progress Scaling System.

---

# Economy Tables

Examples:

- Vendor Multipliers
- Repair Costs
- Construction Costs

Economic rules remain external.

---

# Duration Tables

Examples:

- Crafting Time
- Refining Time
- Building Construction
- Worker Production

---

# Probability Tables

Used when probability changes according to progression.

Examples:

- Rare Drop Bonus
- Gathering Bonus
- Future Event Chances

Version 1 uses these sparingly.

---

# Versioning

Every table contains:

```
Version

↓

Source

↓

Last Modified
```

These values assist balancing workflows.

---

# Runtime Representation

```
Balancing Table

↓

Lookup Request

↓

Value Returned

↓

Gameplay System
```

Tables never contain runtime state.

---

# Validation

Validation checks:

- Unique ID
- Valid Table Type
- Ordered Keys
- Duplicate Keys
- Valid Numeric Values
- Existing References

Invalid tables never load.

---

# Unsupported Features

Version 1 does not support:

- Scripted Curves
- Formula Parsing
- Runtime Editing
- Recursive Tables
- Procedural Balancing
- External Database Queries

# Acceptance Criteria

The Balancing Tables document is complete when:

- Every table has a unique identifier.
- Table Types are predefined.
- Keys are ordered.
- Duplicate keys are rejected.
- Lookup modes are configurable.
- Shared references are supported.
- Runtime state remains separate.
- Validation guarantees integrity.

---

# Immutable Design Rules

Rule 01

Every Balancing Table is completely data-driven.

Rule 02

Gameplay systems never hardcode progression values.

Rule 03

Every scalable value belongs to one Balancing Table.

Rule 04

Tables are referenced exclusively through identifiers.

Rule 05

Lookup keys are deterministic.

Rule 06

Interpolation is optional.

Rule 07

Tables never contain gameplay logic.

Rule 08

Tables never contain runtime state.

Rule 09

Validation prevents duplicate or invalid entries.

Rule 10

Tables remain immutable after loading.

Rule 11

Every table supports versioning.

Rule 12

Every table may declare its content source.

Rule 13

Future balancing categories must remain compatible with the shared data architecture.

Rule 14

Gameplay systems consume tables but never modify them.

Rule 15

Balancing data remains centralized throughout the entire project.

---

# Summary

The Balancing Tables document establishes a centralized, deterministic and fully data-driven architecture for every numerical progression used throughout the game. By separating progression values, scaling curves, multipliers and lookup data from gameplay systems, it creates a single source of truth that simplifies balancing, improves maintainability and allows designers to tune the game's economy, progression and combat without modifying code. This document completes the Data Architecture by providing the mathematical foundation shared across all gameplay systems.
