# 42. BALANCING TABLES

---

# Purpose

This document describes the balancing-data architecture that is actually used by Albion Idle.

The project is data-driven, but it does not require every number to live inside one generic table engine. The source of truth is the authored data/catalog/config module that owns the concern, while gameplay/runtime systems consume that data without carrying zone- or weapon-specific tuning branches.

---

# 1. Rules

1. A tunable value has one authoritative authored source.
2. Gameplay/runtime code must not duplicate tuning data.
3. Renderer/UI code must never own gameplay balance.
4. Benchmarks consume the same authored data and runtime systems as the game whenever possible.
5. A semantic progression contract is documented separately from raw multipliers.
6. Old synthetic snapshots are not balancing tables and must not become sources of truth.
7. Future regions, tiers, weapons and off-hands extend existing catalogs/configs rather than creating mode-specific hardcoded branches.

---

# 2. Current combat balancing sources

ZONE / WORLD-BAND CURVES
Authoritative module:
- packages/data/src/config/combat-progression.ts

Responsibilities:
- segments per zone;
- encounters per segment;
- encounter growth;
- per-world-band zone combat curves;
- health / damage / defense start and end multipliers;
- reward-rank offsets.

Current authored Blue curve:
- Birch Forest: health 0.90 -> 1.08; damage 0.72 -> 0.98; defense 0.90 -> 0.98
- Dark Swamp: health 1.15 -> 1.55; damage 1.18 -> 1.80; defense 1.00 -> 1.10
- Stone Highlands: health 1.70 -> 2.30; damage 2.60 -> 3.00; defense 1.15 -> 1.30
- Golden Steppe: health 2.30 -> 3.02; damage 3.00 -> 3.18; defense 1.30 -> 1.46
- Frostpeak / Mountain: health 3.10 -> 4.00; damage 3.30 -> 3.50; defense 1.50 -> 1.80

These numbers are tuning data. The intended difficulty meaning is defined in 20A_COMBAT_BALANCING_PROCESS.txt.

# 4. Benchmark data architecture

LIVE PLAYER-VS-ZONE BENCHMARK
- apps/client/src/runtime/CombatRuntimeBenchmarkHarness.ts

The harness accepts any authored ZoneDefinitionId and runs the exact live CombatRuntime. It is deliberately world-band agnostic.

WEAPON DIAGNOSTICS
- apps/client/src/data/weaponIdealBenchmark.ts
- apps/client/src/data/weaponPackageBenchmark.ts

The benchmark architecture separates:
- intrinsic weapon offense;
- neutral armor package;
- explicit real loadout including an optional off-hand.

This separation is mandatory for future 1H/off-hand balancing.

---

# 5. How to add a future zone

Do NOT create a new region-specific runtime harness.

Procedure:
1. Author the zone and its placement in the existing world content data.
2. Author/extend its world-band combat curve in combat-progression.ts.
3. Define the expected gear/mastery/potion checkpoints in a zone progression sweep.
4. Call runCombatRuntimeBenchmark with the new ZoneDefinitionId.
5. Compare representative weapons/loadouts.
6. Tune the authored curve only after checking whether an isolated failure is actually a weapon-package issue.
7. Add semantic regression assertions/checkpoints once the contract is validated.

The same process applies to Yellow, Red, Black and future bands.

---

# 6. How to add a future weapon

Procedure:
1. Author item stats, handling, attack speed, abilities and mastery route in existing catalogs/data.
2. Run buildWeaponOnlyBenchmark(...) against the intended comparison set.
3. Run buildWeaponPackageBenchmark(...) with a neutral armor loadout.
4. Run buildWeaponPackageBenchmark(...) again for explicit real loadouts.
5. If the weapon is 1H, test the relevant off-hand combinations explicitly. Never assume that 1H means Reinforced Shield.
6. Validate real progression checkpoints through CombatRuntimeBenchmarkHarness.
7. Accept identity-driven variation when same-class performance remains roughly within the agreed 5-10% envelope or when a larger difference is justified by an explicit package tradeoff.

---

# 7. What belongs in authored balance data

Examples:
- enemy health/damage/defense curves;
- equipment base stats;
- weapon base damage and cadence;
- ability ratios, cooldowns and conditions;
- mastery progression values;
- enchantment scaling;
- potion heal/cooldown values;
- gathering/refining/crafting costs and durations;
- reward/drop/economy values.

What does NOT belong in balance data:
- temporary benchmark compensation;
- renderer-only multipliers;
- weapon-name conditions inside CombatRuntime;
- ACTIVE-only/AFK-only stat hacks;
- duplicated copies of live formulas in tests.

---

# 8. Interpolation and curve semantics

Combat zone curves currently use authored start/end values and the existing progression interpolation/runtime pipeline.

Do not create bespoke per-segment values unless a real design need cannot be represented by the existing curve architecture. Prefer the smallest data-driven curve change that achieves the progression contract.

A structural monotonic curve does not prove good balance. Runtime checkpoint results are the authority for player-facing difficulty.

---

# 9. Versioning / change discipline

For a meaningful balance change:
1. record the design intent;
2. modify the authoritative authored data;
3. run targeted runtime/weapon benchmarks;
4. run regression tests;
5. update 20A when the progression contract changes;
6. update this document only when the balancing architecture/source-of-truth layout changes;
7. append the decision log for durable design changes.

Do not turn every temporary tuning iteration into a permanent design rule.

---

# 10. Current deprecated balance artifacts

The old synthetic combatBalanceMatrix reallocation tool is obsolete and has been removed. It used synthetic hero baselines and partial weapon sets that no longer represent the live game.

The old Blue-specific runtime harness is obsolete and has been replaced by CombatRuntimeBenchmarkHarness so future world bands reuse the exact same tool.

---

# Summary

Albion Idle balance is data-driven through domain-owned catalogs/configuration, validated by a generic live-runtime benchmark and generic weapon-package diagnostics. Future zones and weapons extend these existing sources and tools rather than creating new special-case systems.
