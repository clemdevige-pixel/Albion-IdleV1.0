# 32. DATA CONTENT & ASSET PIPELINE

---

# 1. Purpose

This document defines the complete lifecycle of every non-code resource used by the game.

It covers:

- Content definitions
- Asset management
- Data loading
- Validation
- Registry construction
- Localization
- Hot Reload
- Data generation
- Import / Export
- Versioning
- Build pipeline

Everything that is **not code** passes through this pipeline.

This document is the single source of truth for how content reaches the runtime.

---

# 2. Locked Decisions

The following decisions are immutable.

---

## 2.1 Data Driven Game

The entire gameplay is data-driven.

Gameplay code contains algorithms.

Gameplay data contains values.

Example:

```text
Code

↓

Damage Formula
```

```text
Data

↓

Sword Damage = 34
```

Never:

```ts
if (item == "Sword")
    damage = 34;
```

Always:

```ts
damage = itemDefinition.damage;
```

---

## 2.2 Runtime Formats

Runtime formats are limited to:

```text
JSON
```

CSV exists only for authoring.

Spreadsheet software never becomes a runtime dependency.

---

## 2.3 Single Source of Truth

Every piece of content exists once.

Example:

```text
Broadsword

↓

items/weapons/swords.json
```

Never duplicate values in:

- UI
- Combat
- Loot
- Vendors
- Crafting

Everyone references the same definition.

---

## 2.4 Immutable Definitions

Definitions become immutable after loading.

No runtime system modifies them.

Instead:

```text
Definition

↓

Runtime State
```

Example:

```text
Item Definition

↓

Item Instance
```

---

## 2.5 Human Readable IDs

Every content entry owns one stable textual ID.

Example:

```text
enemy_skeleton_archer

item_broadsword_t5

ability_fireball

resource_ore_t6
```

IDs never change after release.

---

## 2.6 One Family = One Registry

Each family owns exactly one registry.

Examples:

```text
Item Registry

Enemy Registry

Zone Registry

Recipe Registry

Effect Registry
```

---

## 2.7 Registry Read Only

Registries expose read operations only.

No runtime insertion.

No runtime deletion.

No runtime modification.

---

## 2.8 Content Never References Runtime Objects

Definitions reference only IDs.

Forbidden:

```ts
enemy.target = player
```

Allowed:

```json
{
    "abilityId": "ability_fireball"
}
```

---

## 2.9 Validation Before Loading

Invalid content never reaches runtime.

Validation is mandatory.

---

# 45. Acceptance Criteria

The pipeline is complete when

- Every family loads through the same system.
- All registries are immutable.
- Every reference is validated.
- Duplicate IDs are impossible.
- Assets are manifest-driven.
- Localization is key-based.
- CSV always passes through JSON.
- Runtime never parses spreadsheets.
- Runtime never scans folders.
- Registry lookup is O(1).
- Invalid content never reaches gameplay.
- Hot Reload is atomic.
- Generated files are reproducible.
- One definition has exactly one source of truth.

---

# 46. Final Summary

The game uses a fully data-driven architecture.

Every resource follows the same lifecycle.

```text
Author

↓

Validation

↓

Registry

↓

Runtime

↓

Read Only Access
```

Gameplay code consumes validated definitions.

It never embeds gameplay values.

Assets are manifest-driven.

Localization is key-driven.

Registries are immutable.

This guarantees deterministic gameplay, simple tooling, safe Hot Reload and scalable content production.
