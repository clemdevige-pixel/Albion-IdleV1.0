# 33. BACKEND API & PERSISTENCE

---

# 1. Purpose

This document defines the complete backend architecture.

It specifies:

- Server responsibilities
- API architecture
- Authentication
- Authorization
- Persistence
- Database design
- Transactions
- Save system
- Repository contracts
- Security
- Versioning
- Audit
- Anti-cheat
- Scalability

The backend is the authoritative source of truth for all persistent gameplay.

---

# 2. Locked Decisions

---

## 2.1 Server Authority

The server owns every persistent gameplay state.

The client never validates gameplay.

The client never computes rewards.

The client never decides progression.

The client only sends player intent.

---

## 2.2 Stateless API

HTTP requests are stateless.

Every request contains enough information to authenticate and execute independently.

No gameplay state is stored inside HTTP sessions.

---

## 2.3 Database

Only one database exists.

```text
PostgreSQL
```

Every persistent system stores its data there.

No gameplay state is stored in JSON files.

---

## 2.4 ORM

Prisma is the only ORM.

Repositories never expose Prisma models.

---

## 2.5 Transactions

Every multi-step mutation is atomic.

Either:

```text
Everything succeeds
```

or

```text
Everything rolls back
```

---

## 2.6 No Trust In Client

The backend never trusts:

- timestamps
- damage
- rewards
- item quality
- currency
- mastery
- loot
- combat result

Everything is recalculated.

---

## 2.7 Save Ownership

Only the backend writes saves.

Clients never upload complete save files.

---

↓

↓

# 10. Request Validation

Every request passes Zod validation.

```text

```

No invalid request reaches domain logic.

# 48. Acceptance Criteria

Backend is complete when

- Every mutation is transactional.
- Client cannot forge rewards.
- Save is authoritative.
- JWT authentication works.
- Requests are validated.
- DTOs isolate persistence.
- Repositories hide Prisma.
- Database uses indexes.
- Idempotent endpoints are safe.
- Optimistic concurrency prevents overwrites.
- Audit exists for sensitive operations.
- Background progression uses timestamps.
- Save migrations are supported.
- Health checks are available.
- Monitoring exposes runtime health.

---

# 49. Final Summary

The backend follows a strict server-authoritative architecture.

```text
Intent

↓

Validation

↓

Authentication

↓

Authorization

↓

Use Case

↓

Domain

↓

Transaction

↓

Persistence

↓

DTO

↓

Client
```

Persistent state is normalized.

Every mutation is atomic.

The client is never trusted.

The server owns all gameplay progression, rewards and saves.

This architecture guarantees consistency, security and scalability while remaining simple enough for Version 1.
