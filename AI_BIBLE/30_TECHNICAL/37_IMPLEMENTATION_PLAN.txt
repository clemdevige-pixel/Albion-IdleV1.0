# 37. IMPLEMENTATION PLAN

---

# 1. Purpose

This document defines the exact implementation order of the project.

It answers one question:

> **What should Claude implement next?**

The objective is to:

- Minimize refactoring
- Avoid circular dependencies
- Keep every build playable
- Validate each system before adding the next one
- Deliver a Vertical Slice as early as possible

This document is the implementation roadmap for the entire codebase.

---

# 2. Core Principles

The project follows these rules.

---

## 2.1 Vertical Slice First

The goal is **not** to finish one entire system before another.

Instead:

```text
Infrastructure

↓

Minimal Gameplay

↓

Playable Slice

↓

Expand
```

---

## 2.2 Build on Stable Foundations

Every phase depends only on previous validated phases.

Never implement a feature whose dependencies are missing.

---

## 2.3 Always Playable

After every milestone:

- The project builds.
- The game launches.
- Existing features still work.

---

## 2.4 One Responsibility Per Phase

Each phase has one objective.

Example:

```text
Combat

≠

Inventory

≠

Crafting
```

Avoid mixing unrelated systems.

---

## 2.5 No Placeholder Gameplay

Temporary assets are acceptable.

Temporary gameplay logic is not.

Claude must implement the real architecture immediately, even if some values are placeholders.

# 24. Definition of Done

A feature is complete only if:

- Architecture matches the Bible.
- Code compiles.
- Tests pass.
- Lint passes.
- Typecheck passes.
- Documentation updated.
- No TODO blocks critical gameplay.
- No placeholder gameplay logic remains.
- Performance targets are respected.
- No regression introduced.

---

# 25. Feature Checklist

Before implementing any feature, Claude must verify:

```text
□ Dependencies implemented

□ Data schema exists

□ Runtime architecture exists

□ Persistence defined

□ DTOs defined

□ Tests planned

□ Assets available or placeholder registered

□ Localization keys defined
```

---

# 26. Code Review Checklist

Every pull request should verify:

- Naming consistency
- Module boundaries
- No duplicated logic
- No forbidden imports
- Proper validation
- Transaction safety
- Error handling
- Test coverage
- Documentation updated

---

# 27. Asset Readiness Checklist

A gameplay feature using visuals is considered ready when:

```text
□ Asset ID defined

□ Manifest entry exists

□ Placeholder or final asset available

□ Animation IDs registered

□ Localization keys created

□ Asset referenced by definition, never by path
```

---

# 28. Data Readiness Checklist

Before adding new content:

```text
□ Definition ID unique

□ Schema valid

□ References valid

□ Localization complete

□ Asset references valid

□ Registry loads successfully
```

---

# 29. Release Readiness Checklist

Before a public release:

```text
□ All automated tests pass

□ Content validation passes

□ Asset validation passes

□ Save migration tested

□ Smoke tests pass

□ Performance budgets respected

□ Backup verified

□ Monitoring active

□ Version numbers updated

□ Changelog written
```

# 30. Acceptance Criteria

The implementation plan is complete when:

- Every phase has a clear objective.
- Dependencies are respected.
- Vertical Slice is delivered early.
- Every milestone is playable.
- No gameplay system is implemented before its foundation.
- Checklists define objective completion.
- Claude can determine the next implementation step without ambiguity.
