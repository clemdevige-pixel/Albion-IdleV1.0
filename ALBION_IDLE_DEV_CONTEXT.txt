16) WEAPON PIPELINE GLOBAL CONTRACT TEST
Date/session: 2026-08-10
Status: implementation committed; Vercel/test validation pending.

Trigger:
The first Dagger Pair end-to-end implementation exposed a remaining hidden UI dependency: gameplay/mastery content was correct, but the Masteries panel had a stale closed family list. This proved a cross-system contract test is now valuable before scaling weapon content production.

Objective:
Add one global automated contract that derives its subject list from WEAPON_ITEM_DEFINITIONS and fails whenever any declared weapon is only partially integrated into the generic pipeline.

File added:
- apps/client/src/data/weaponPipeline.contract.test.ts

Contract coverage for every declared weapon item:
- tier resolver exists.
- Item Power exists.
- equipment definition exists and resolves to weapon slot.
- family route exists and points to a declared WEAPON_FAMILIES entry.
- family mastery and specialization mastery definitions exist.
- combat profile and positive intrinsic attack speed exist.
- primary ability route and CLIENT_ABILITIES definition exist.
- exactly one vendor offer exists.
- exactly one equipment craft recipe exists.
- presentation exists with non-empty item icon, actor manifest and combat presentation profile.
- repair recognizes the item as a weapon at the correct tier.
- enchantment recognizes the correct tier; T3 remains non-enchantable and T4 remains enchantable in the current V1 slice.
- standard craft items must belong to STANDARD_WEAPON_CRAFT_RECIPES.
- standard T3 recipes must contain no weapon predecessor.
- standard T4 recipes must contain exactly the catalog-resolved T3 predecessor x1.
- artifact_pending weapons must remain outside the standard generator.

Masteries UI contract coverage:
- builds the actual buildMasteriesModel using synthetic state generated from WEAPON_MASTERY_DEFINITIONS.
- every catalog family must appear in Combat masteries.
- family display name must match WEAPON_FAMILIES.
- family presentation/icon must resolve.
- every catalog specialization must appear under exactly its catalog family topology.

Important design rule:
The contract test contains no hand-authored list of weapon item IDs or weapon family IDs. Adding a new weapon/family automatically expands the test surface through the authoritative catalogs. This is specifically intended to catch future omissions like the Dagger Pair Masteries UI issue before deployment/manual smoke testing.

No runtime/gameplay/balance change.
