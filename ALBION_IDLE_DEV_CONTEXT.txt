AUDIT — WEAPON CONTENT PIPELINE
-------------------------------
Audit completed before refactor. No code changes made during audit.

Current strong central boundary:
apps/client/src/data/weaponContentCatalog.ts

It already defines/generates much of:
- item equipment definitions
- primary abilities
- mastery family + specialization routing
- mastery display names
- mastery definitions
- vendor sell offers

Remaining duplicated/manual weapon data identified in:
- apps/client/src/data/itemPower.ts
  - ITEM_TIERS
  - WEAPON_MASTERY_BY_ITEM
  - WEAPON_PROFILE_BY_ITEM
- apps/client/src/panels/ItemVisual.tsx
  - name/icon/tier/slot/handling/stats duplicated per item
- apps/client/src/data/refiningRecipes.ts
  - craft recipes are manually authored
- apps/client/src/data/equipmentPresentation.ts
  - item -> actor manifest / combat presentation mapping
- apps/client/src/data/progressionContentCatalog.ts
  - individual mastery constants/definitions/display switch duplicate generated weapon masteries
- apps/client/src/game/GameBridge.ts
  - crafting family union is hardcoded
- apps/client/src/ui/production/crafting/craftingModels.ts
  - crafting family presentation is hardcoded
- content/data/items.json
- content/data/equipment.json
- content/data/recipes.json
  - these currently contain weapon data that diverges from the live runtime and must not be treated as authoritative without reconciliation

Important audit finding:
content/data/equipment.json currently contains weapon values that differ from live runtime values. Example: Broadsword T4 values do not match weaponContentCatalog.ts. These JSON files are therefore currently parallel/stale content sources, not safe authoring boundaries.

Another audit finding:
WEAPON_MASTERY_DEFINITIONS currently detects specialization masteries via a hardcoded list of mastery IDs. This must be derived from familyMasteryId vs specializationMasteryId instead before scaling weapon content.

Combat architecture findings:
- AutoAttackManager is generic and uses stat_attack_speed.
- CombatService chooses physical vs magical basic attack based on computed offensive stats.
- CombatRuntime resolves the equipped weapon primary ability generically.
- CombatRewardRuntime resolves family + specialization mastery generically for Fame.
- EquipmentManager does not require weapon-specific code.
- CraftingRuntime is generic and should not require weapon-specific code.
- EnchantmentService is generic and should not require weapon-specific code.
- Repair/durability is generic by equipment category/tier.
- Persistence is item/instance based and should not need weapon-specific modifications.
- GameScene must never gain weapon-specific conditions again.

Presentation architecture findings:
- equipmentPresentation.ts maps item -> actorManifestId + combatProfileId.
- Render manifests define idle/walk/attack/death and visual profile parameters.
- Ranged weapons additionally use a combat presentation profile + projectile manifest.
- CombatPresentationSystem is generic and should remain weapon-name agnostic.
- defaultRenderManifestRegistry registers actor/projectile manifests.

METHODOLOGY LESSONS FROM CURRENT BRANCH
----------------------------------------
- Never assume a legacy component is still mounted because its name matches the feature.
- Follow the real render path before editing UI.
- Prefer existing gameplay actions/managers over recreating logic in React.
- Prefer portal-based floating UI when the active shell has nested overflow/layout contexts.
- If a rule already has a central constant/catalog, change that authority rather than adding conditionals to callers.
- New weapon support must not reintroduce special cases into GameScene or CombatRuntime unless the mechanic itself is genuinely new.
