8) WEAPON PIPELINE STEP 5 — PRESENTATION AUTHORITY BY SPECIALIZATION
Date/session: 2026-08-10
Status: implementation pushed; Vercel/manual validation pending.

Objective:
Reduce presentation duplication so every weapon specialization owns one explicit presentation definition reused by all tiers, without making actor/projectile assets implicit.

Audit findings before modification:
- equipmentPresentation.ts duplicated the same actorManifestId/combatProfileId for each T3/T4 item of a specialization.
- ItemVisual.tsx separately maintained a second specialization map solely for item icons.
- active consumers already go through resolveEquipmentPresentation for bridge synchronization and CharacterModule hero idle preview.
- ranged combat profiles/projectile IDs belong to the renderer profile layer and should remain separate from weapon identity; they are not duplicated item metadata.

Files modified:
- apps/client/src/data/equipmentPresentation.ts
- apps/client/src/panels/ItemVisual.tsx
- apps/client/src/data/equipmentPresentation.test.ts (new)
- ALBION_IDLE_DEV_CONTEXT.txt

New presentation model:
- one explicit presentation definition per specialization mastery ID.
- each definition contains:
  - itemIcon
  - actorManifestId
  - combatProfileId
- resolveEquipmentPresentation(itemId) first resolves the weapon specialization through weaponContentCatalog, then returns that specialization's presentation.
- no per-tier presentation item map remains.

Current specialization presentation choices preserved exactly:
- Broadsword -> item-broadsword-pixel-v1.png / hero_broadsword / melee
- Longbow -> item-longbow-pixel-v1.png / hero_bow / bow
- Badon -> item-badon-pixel-v1.png / hero_bow / badon
- Fire Staff -> item-fire-staff-pixel-v1.png / hero_fire_staff / fire_staff
- Spiked Gauntlets -> item-spiked-gauntlets-pixel-v1.png / hero_spiked_gauntlets / melee

ItemVisual cleanup:
- removed WEAPON_ICON_BY_SPECIALIZATION.
- weapon icon now comes from resolveEquipmentPresentation(itemId).itemIcon.
- tier/handling/stats/name still derive from weaponContentCatalog as before.
- therefore a specialization now has one presentation authoring location for item icon + equipped actor + combat presentation profile.

Tests added:
- T3/T4 of the same specialization resolve to identical presentation definitions.
- Broadsword and Badon explicit presentation values are locked.
- unknown weapon IDs do not receive inferred presentation.

Important boundary retained:
- combatPresentationProfiles.ts remains authoritative for ranged profile -> projectile/release timing.
- render manifests remain authoritative for actual animation asset paths/frame data.
- adding a new unique ranged weapon may still require a new combat presentation profile + projectile manifest/assets; that is genuine presentation content, not duplicated weapon metadata.

Validation requested:

- inventory icons unchanged.
- CharacterModule hero preview unchanged for each current weapon.
- combat actor/animation unchanged.
- Longbow/Badon/Fire Staff projectiles unchanged.

METHODOLOGY LESSONS
-------------------
- Never assume a legacy component is mounted because its name matches the feature.
- Follow the real render path before editing UI.
- Prefer existing managers/actions over recreating logic.
- Modify authoritative catalogs rather than adding caller conditionals.
- GameScene/CombatRuntime must not gain weapon-name special cases for content additions.
- Search all consumers before deleting exports.
- Separate gameplay metadata from presentation-only metadata.
- Audit aggregate registries for hidden re-declarations after spreads.
- A standard T4+ weapon without its T(n-1) specialization item is invalid content and should fail generation loudly.
- Do not simulate future artifact mechanics with fake generic rules; keep artifact weapons explicitly outside the standard pipeline until their system exists.
- Presentation should be authored by specialization, not copied once per tier; actual renderer profiles/manifests remain explicit because those differences are real content.
