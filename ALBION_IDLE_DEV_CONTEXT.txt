INITIAL WEAPON PIPELINE AUDIT
-----------------------------
Strong central boundary identified:
apps/client/src/data/weaponContentCatalog.ts

It already defined/generated:
- weapon equipment definitions
- primary abilities
- mastery family + specialization routing
- mastery display names
- mastery definitions
- vendor sell offers

Duplicated/manual weapon data identified in:
- apps/client/src/data/itemPower.ts
  - ITEM_TIERS weapon entries
  - WEAPON_MASTERY_BY_ITEM
  - WEAPON_PROFILE_BY_ITEM
- apps/client/src/panels/ItemVisual.tsx
  - name/icon/tier/slot/handling/stats duplicated per weapon
- apps/client/src/data/refiningRecipes.ts
  - craft recipes manually authored
- apps/client/src/data/equipmentPresentation.ts
  - item -> actor manifest / combat presentation mapping
- apps/client/src/data/progressionContentCatalog.ts
  - individual weapon mastery constants/definitions/display switch
- apps/client/src/game/GameBridge.ts
  - crafting family union hardcoded
- apps/client/src/ui/production/crafting/craftingModels.ts
  - crafting family presentation hardcoded
- content/data/items.json
- content/data/equipment.json
- content/data/recipes.json
  - parallel/stale weapon content; values can diverge from live runtime

Important audit findings:
- content/data/equipment.json currently differs from live runtime values (example: Broadsword T4), so it is not a safe current authoring source.
- WEAPON_MASTERY_DEFINITIONS previously detected specialization masteries via hardcoded mastery ID names.
- weaponContentCatalog previously generated abilities but then manually redeclared the same abilities.
- resolvePrimaryAbilityId and resolveWeaponMastery previously had item-name/switch fallbacks even though all live weapons already existed in the catalog.

Combat architecture findings:
- AutoAttackManager is generic and uses stat_attack_speed.
- CombatService chooses physical vs magical basic attack from computed offensive stats.
- CombatRuntime resolves equipped weapon primary ability generically.
- CombatRewardRuntime resolves family + specialization mastery generically for Fame.
- EquipmentManager, CraftingRuntime, EnchantmentService and repair/persistence should not need weapon-name special cases.
- GameScene must never gain weapon-specific conditions again.

Presentation architecture findings:
- equipmentPresentation.ts maps item -> actorManifestId + combatProfileId.
- Render manifests define idle/walk/attack/death and visual parameters.
- Ranged weapons additionally use combat presentation profiles + projectile manifests.
- CombatPresentationSystem is generic and must remain weapon-name agnostic.

4) WEAPON CONTENT PIPELINE REFACTOR — STEP 1
Date/session: 2026-08-10
Status: code implemented; automated build/test validation pending Vercel/CI result.

Objective:
Make weaponContentCatalog the authoritative source for weapon gameplay identity metadata before touching craft/UI presentation metadata.

Files modified:
- apps/client/src/data/weaponContentCatalog.ts
- apps/client/src/data/itemPower.ts
- apps/client/src/data/weaponContentCatalog.test.ts (new)

weaponContentCatalog changes:
- WeaponCombatProfile moved to the weapon catalog.
- WEAPON_ATTACK_SPEED_BY_PROFILE moved to the weapon catalog.
- Each specialization now explicitly declares combatProfile.
- Each weapon item now explicitly declares tier.
- Removed duplicated CLIENT_ABILITIES manual redeclarations; CLIENT_ABILITIES now derives directly from WEAPON_CONTENT.
- Removed item-name fallback logic from resolvePrimaryAbilityId.
- Removed hardcoded item switch fallback from resolveWeaponMastery.
- Added resolveWeaponTier(itemId).
- Added resolveWeaponCombatProfile(itemId).
- Added resolveWeaponAttackSpeed(itemId).
- Internal item lookup now stores both specialization metadata and item-tier metadata.
- WEAPON_MASTERY_DEFINITIONS now derives family vs specialization categories from explicit familyMasteryIds/specializationMasteryIds sets, not mastery-name substring lists.

itemPower changes:
- Removed all weapon entries from the local ITEM_TIERS table.
- Renamed remaining table conceptually to NON_WEAPON_ITEM_TIERS.
- Removed local WEAPON_MASTERY_BY_ITEM duplication.
- Removed local WEAPON_PROFILE_BY_ITEM duplication.
- Removed local attack speed profile table duplication.
- getItemTier now resolves weapon tier through weaponContentCatalog and falls back only for non-weapon equipment.
- getWeaponMasteryIds now adapts resolveWeaponMastery from weaponContentCatalog.
- getWeaponCombatProfile/getWeaponAttackSpeed now delegate to weaponContentCatalog.
- No intended balance changes: existing T3/T4 tiers, mastery routes and attack speeds are preserved exactly.

Tests added:
weaponContentCatalog.test.ts verifies all currently supported weapon items:
- tier;
- combat profile;
- attack speed;
- family mastery;
- specialization mastery;
- primary ability;
- ability registry presence.
It also verifies family/specialization mastery categories and verifies that unknown fake weapon IDs are no longer inferred from naming conventions.

Validation state:
- Source-level audit complete.
- No deliberate gameplay/balance changes in this step.
- Await Vercel/typecheck/test status after latest commit before declaring step fully validated.

Why this step matters:
A future weapon added to WEAPON_CONTENT no longer requires manually synchronizing tier, mastery route or attack profile in itemPower.ts. Unknown item IDs also no longer silently receive behavior merely because their string contains _sword_, _bow_, _staff_ or _gloves_.
