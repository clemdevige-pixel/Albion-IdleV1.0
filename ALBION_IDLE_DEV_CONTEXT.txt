Important audit findings:
- content/data/equipment.json differs from live runtime values and is not a safe current authoring source.
- weapon mastery category detection contained hardcoded mastery names.
- abilities were generated and then redeclared manually.
- itemPower duplicated weapon tier/mastery/profile mappings.
- progressionContentCatalog re-added weapon mastery definitions already generated by weaponContentCatalog.
- progressionContentCatalog duplicated weapon mastery display names in a switch.

Combat architecture findings:
- AutoAttackManager is generic and uses stat_attack_speed.
- CombatService chooses physical vs magical basic attack from computed offensive stats.
- CombatRuntime resolves equipped weapon primary ability generically.
- CombatRewardRuntime resolves family + specialization mastery generically for Fame.
- EquipmentManager, CraftingRuntime, EnchantmentService and repair/persistence should not need weapon-name special cases.
- GameScene must never gain weapon-specific conditions again.

Presentation architecture findings:
- equipmentPresentation.ts maps item -> actorManifestId + combatProfileId.
- Render manifests define idle/walk/attack/death and visual parameters.
- Ranged weapons additionally use combat presentation profiles + projectile manifests.
- CombatPresentationSystem is generic and must remain weapon-name agnostic.

5) WEAPON CONTENT PIPELINE REFACTOR — STEP 2
Date/session: 2026-08-10
Status: implementation corrected after build regression; Vercel validation pending.

Objective:
Remove duplicated weapon mastery definitions/names/constants from progressionContentCatalog so weaponContentCatalog is the sole authoring source for weapon progression definitions.

Audit before modification:
- MASTERY_DEFINITIONS already spread WEAPON_MASTERY_DEFINITIONS and then manually re-added the same weapon family/specialization definitions.
- getMasteryDisplayName already consulted getWeaponMasteryDisplayName before a duplicate weapon-name switch.
- gathering definitions were also duplicated after already being spread.

Files modified:
- apps/client/src/data/progressionContentCatalog.ts
- apps/client/src/data/progressionContentCatalog.test.ts

Changes:
- MASTERY_DEFINITIONS now composes WEAPON_MASTERY_DEFINITIONS + GATHERING_MASTERY_DEFINITIONS exactly once.
- duplicate weapon mastery definitions removed.
- duplicate gathering definitions removed.
- weapon mastery display names resolve from weaponContentCatalog.
- gathering display names remain owned by gathering progression content.
- new tests verify uniqueness, categories and display names.

BUILD REGRESSION FOUND AFTER STEP 2:
Vercel error:
"src/state/GameContext.tsx: SWORD_MASTERY_ID is not exported by src/data/progressionContentCatalog.ts"

Root cause:
- the initial Step 2 audit incorrectly concluded the removed weapon mastery constants had no external consumers.
- GameContext still imports SWORD_MASTERY_ID and BROADSWORD_MASTERY_ID for starter Broadsword mastery discovery.
- the first failing commit caused all subsequent Step 2 commits to fail as descendants.

Correction applied:
- SWORD_MASTERY_ID and BROADSWORD_MASTERY_ID are restored only as compatibility exports for current GameContext bootstrap.
- their values are NOT re-authored/hardcoded in progressionContentCatalog.
- both are derived from resolveWeaponMastery("item_weapon_sword_t3_broadsword") in weaponContentCatalog.
- module throws immediately if the starter weapon route is missing, preventing silent drift.
- no duplicate mastery mapping/source of truth was reintroduced.

Remaining architectural cleanup:
- later in the weapon pipeline refactor, GameContext starter bootstrap should consume the weapon catalog route directly so these compatibility aliases can be removed entirely.

Validation state:
- exact Vercel compile error identified and corrected.
- Vercel rebuild pending after fix.
- manual mastery/Fame smoke test required after successful deployment.

METHODOLOGY LESSONS
-------------------
- Never assume a legacy component is mounted because its name matches the feature.
- Follow the real render path before editing UI.
- Prefer existing gameplay actions/managers over recreating logic in React.
- If a rule already has a central constant/catalog, change that authority rather than adding conditionals to callers.
- New weapon support must not reintroduce special cases into GameScene or CombatRuntime unless the mechanic itself is genuinely new.
- Before deleting an exported symbol, search not only the defining module but all consumers on the active branch and verify the actual build dependency path.
