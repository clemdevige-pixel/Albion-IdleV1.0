# Executive Summary

Le projet est aujourd'hui dans une situation très différente de ce que pourrait laisser penser la roadmap historique.

Cela signifie que les prochaines semaines ne consisteront plus à "construire le moteur", mais à remplir progressivement ce moteur avec du contenu et des fonctionnalités.

- modifier l'architecture chaque semaine

---

# Philosophie de développement à partir de maintenant

Chaque nouvelle fonctionnalité devra respecter quatre règles :

1. Ne jamais casser l'architecture existante.

2. Réutiliser les systèmes déjà présents avant d'en créer de nouveaux.

3. Ajouter du contenu avant de réécrire du code.

4. N'entreprendre une refonte que lorsqu'un blocage technique réel est identifié.

Ces quatre règles devront guider l'ensemble du développement jusqu'à la V1.

# 1. Combat

## Modules concernés

```text
combat/
damage/
auto-attack/
targeting/
abilities/
effects/
death/
```

## Fondations présentes

Le dépôt contient des éléments dédiés à :

- l’orchestration des combats ;
- la gestion d’une session de combat ;
- les états du combat ;
- le calcul et l’application des dégâts ;
- la validation des attaques ;
- les délais des attaques automatiques ;
- la sélection des cibles ;
- les capacités ;
- les temps de recharge ;
- les effets ;
- la mort ;
- la génération et le transfert du loot.

## Niveau de maturité

**Fondation avancée, intégration complète à certifier.**

Le combat est visible dans le client et constitue déjà une partie jouable du projet.

Il reste cependant à vérifier précisément :

- que les statistiques d’équipement alimentent toujours correctement les dégâts ;
- que les attaques automatiques utilisent une source unique pour leur vitesse et leurs dégâts ;
- que les capacités actives et passives sont entièrement reliées aux armes ;
- que les effets temporaires sont sauvegardés ou volontairement exclus ;
- que la mort interrompt correctement toutes les actions ;
- que le loot est transféré sans duplication ;
- que les combats reprennent proprement après un changement de zone ou un chargement.

## Risques

- logique répartie entre gameplay, `GameContext`, bridge et présentation ;
- calculs visuels pouvant diverger des calculs réels ;
- événements de combat déclenchés plusieurs fois ;
- états intermédiaires mal réinitialisés ;
- cooldowns ou timers non restaurés correctement.

## Priorité

**P1 — Certifier l’intégration, sans réécrire le système.**

# 2. Personnage et statistiques

## Modules concernés

```text
character/
```

## Fondations présentes

- des composants ECS ;
- un système de statistiques ;

- une synchronisation équipement → statistiques ;
- une sauvegarde de l’équipement.

## Niveau de maturité

**Fondation solide, cohérence des sources à vérifier.**

## Points à contrôler

- origine exacte des PV, dégâts et défense ;
- ordre d’application des bonus ;
- recalcul après changement d’équipement ;
- conservation du pourcentage de PV lors d’une variation des PV maximum ;
- influence des maîtrises ;
- influence de la qualité et de l’enchantement ;
- comportement après chargement d’une sauvegarde ;

````markdown
# PARTIE 5 — AUDIT DU CLIENT REACT, DE L’UI ET DU BRIDGE

---

# Objectif

Cette partie analyse les couches suivantes :

```text
apps/client/src/state/
apps/client/src/game/
apps/client/src/hud/
apps/client/src/layout/
apps/client/src/panels/
apps/client/src/data/

L’objectif est de déterminer :

- où se trouve la logique métier ;

- comment Phaser reçoit les informations de présentation ;
- quelles responsabilités sont trop centralisées ;
- quelles priorités doivent guider les prochaines missions Work.

# 1. Architecture générale du client

Le client repose sur plusieurs couches principales :

```text
React
│
├── Layout
├── HUD
├── Panels
├── State
└── View-models
        │
        ▼
GameBridge
        │
        ▼
Runtime gameplay
        │
        ▼
Presentation Runtime
        │
        ▼

```

Cette architecture est cohérente avec la cible définie pour Albion Idle :

- React gère les menus, panneaux et contrôles ;
- Phaser gère la scène, les personnages, les animations et les effets ;
- le gameplay reste indépendant ;
- le bridge traduit l’état runtime vers des données exploitables par l’affichage.

Le problème principal ne vient pas de cette séparation théorique.

Il vient du volume de responsabilités encore concentré dans certains fichiers du client.

# 2. `GameContext.tsx`

## Rôle actuel

`GameContext.tsx` semble être le point central d’assemblage du client.

Il importe et coordonne notamment :

- le runtime ECS ;
- les systèmes de combat ;
- les systèmes de progression ;
- l’inventaire ;
- la banque ;
- l’équipement ;
- les statistiques ;
- les monnaies ;
- les vendeurs ;
- la réparation ;
- le gathering ;
- le refining ;
- le crafting ;
- les workers ;
- les zones ;
- la progression monde ;
- la sauvegarde ;
- les catalogues de contenu ;
- la synchronisation avec `GameBridge`.

Les erreurs TypeScript rencontrées lors du build se situaient jusqu’à plus de 3 500 lignes dans ce fichier.

Cela confirme qu’il est devenu très volumineux.

---

## Diagnostic

`GameContext.tsx` est actuellement le principal point de dette technique du client.

Un Context React devrait principalement :

- fournir un accès à un état ;
- exposer des commandes ;
- gérer le cycle de vie React ;
- connecter les composants au runtime.

Il ne devrait pas :

- créer tous les managers métier ;
- contenir des règles de progression ;
- définir des recettes ou du contenu ;
- mapper tous les domaines ;
- gérer seul la sauvegarde ;
- orchestrer toutes les transactions ;
- reconstruire des types métier.

---

## Conséquences actuelles

### 1. Faible lisibilité

Une modification locale nécessite de comprendre un très grand fichier.

### 2. Effet domino

L’ajout d’une profession ou d’une famille d’équipement peut provoquer des erreurs dans plusieurs zones éloignées du fichier.

### 3. Faible testabilité

Il est difficile d’instancier une partie du client sans créer tout le contexte.

### 4. Coût Work élevé

Work doit lire beaucoup de code avant de pouvoir modifier une petite fonctionnalité.

### 5. Risque de duplication

Le fichier peut contenir des règles ou données déjà présentes dans les packages gameplay ou data.

---

## Cible recommandée

Créer une couche indépendante de React :

```text
GameClientRuntime
```

Cette couche doit :

- instancier les services ;
- gérer les dépendances ;
- démarrer et arrêter le runtime ;
- exposer des commandes métier ;
- exposer les abonnements nécessaires ;
- coordonner la sauvegarde ;
- rester testable sans React.

`GameContext` deviendrait alors :

```text
création du GameClientRuntime
+ abonnement React
+ exposition de l’état
+ exposition des commandes
+ nettoyage au démontage
```

---

## Découpage progressif recommandé

Le refactor ne doit pas être une réécriture massive.

Ordre recommandé :

```text
1. Cartographier GameContext
2. Créer GameClientRuntime
3. Déplacer l’initialisation
4. Extraire CombatRuntimeModule
5. Extraire ProgressionRuntimeModule
6. Extraire EconomyRuntimeModule
7. Extraire ProductionRuntimeModule
8. Extraire WorkerRuntimeModule
9. Extraire PersistenceRuntimeModule
10. Alléger GameContext
```

---

## Priorité

**P0/P1**

Le fichier ne bloque pas immédiatement le jeu, mais il bloquera rapidement la vitesse de développement.

# 3. `GameBridge.ts`

## Rôle

`GameBridge.ts` semble fournir l’état consommé par les différentes couches d’affichage.

- des types de view-models ;
- un état global ;
- des valeurs par défaut ;
- des méthodes de mise à jour ;
- des abonnements ;
- des snapshots ;
- des notifications vers React.

## Points positifs

- possibilité pour React de s’abonner ;
- découplage partiel avec Phaser ;
- centralisation de l’état de présentation ;
- utilisation adaptée à `useSyncExternalStore`.

---

## Problèmes constatés

### 1. Unions de types dupliquées

Exemple déjà rencontré :

```ts
export type WorkerProfessionVM =
  | "woodcutter"
  | "miner"
  | "stonecutter"
  | "skinner"
  | "fiber_harvester";
```

Le type UI doit rester synchronisé avec le type gameplay.

Le problème `stonecutter` a montré que cette synchronisation manuelle est fragile.

### 2. État global très large

Un bridge unique peut progressivement devenir difficile à maintenir.

### 3. Valeurs par défaut métier

Les valeurs initiales du bridge peuvent contenir des hypothèses de gameplay qui devraient provenir du runtime ou des données.

### 4. Responsabilités multiples

Le bridge peut finir par gérer :

- état ;
- mapping ;
- fallback ;
- logique d’affichage ;
- règles métier.

```text
CharacterBridgeSlice
CombatBridgeSlice
InventoryBridgeSlice
ProductionBridgeSlice
WorkerBridgeSlice
WorldBridgeSlice
ProgressionBridgeSlice
```

Chaque slice contient :

- ses view-models ;
- son état ;
- ses mises à jour ;
- ses mappers ;
- ses tests.

`GameBridge` reste l’agrégateur.

---

## Règle importante

Le bridge ne doit jamais décider :

- si une action est autorisée ;
- combien coûte un craft ;
- combien de dégâts sont infligés ;
- quelle zone est débloquée ;
- quelle récompense est accordée.

Il doit uniquement traduire et exposer.

Cette couche est nécessaire.

Le problème n’est pas son existence, mais son potentiel de concentration.

## Risques

Une nouvelle valeur gameplay peut ne pas être prise en charge côté UI.

### 2. Valeurs par défaut silencieuses

### 3. Logique métier dans le mapping

Un mapper peut commencer à recalculer une valeur au lieu de la recevoir du gameplay.

### 4. Types implicites

Des erreurs `any` ont été observées dans ce fichier lors du build.

### 5. Couplage transversal

Une modification d’inventaire peut forcer une modification du bridge global.

---

```text
bridge/

  syncInventory.ts
  syncEquipment.ts
  syncEconomy.ts
  syncProduction.ts
  syncWorkers.ts
  syncWorld.ts
  syncProgression.ts
```

Chaque mapper doit être :

- pur ;
- typé ;
- exhaustif ;
- sans effet de bord ;
- testé.

---

## Exemple de règle

Une fonction de synchronisation doit recevoir :

```ts
GameplayState
```

et retourner :

```ts
ViewModel
```

Elle ne doit pas :

- modifier l’inventaire ;
- déclencher un craft ;
- appliquer des dégâts ;
- sauvegarder la partie ;
- appeler Phaser.

**P1**
````

````markdown
# PARTIE 8 — AUDIT DE LA PERSISTENCE, DE LA SAUVEGARDE ET DE L’AUTHENTIFICATION

---

# Objectif

Cette partie analyse la capacité d’Albion Idle à :

- sauvegarder durablement la progression ;
- restaurer une partie après fermeture du navigateur ;
- faire évoluer le format de sauvegarde ;
- gérer les sauvegardes corrompues ;
- calculer la progression hors-ligne ;
- préparer une future sauvegarde cloud ;
- intégrer ultérieurement une authentification.

La sauvegarde constitue un élément critique pour un idle game.

Une perte de progression peut suffire à rendre une version inutilisable, même si tous les autres systèmes fonctionnent correctement.

---

# 1. Architecture actuelle

Le dépôt contient un package dédié :

```text
packages/persistence/
```

Il comprend notamment :

```text
serializer
deserializer
save-manager
save-provider
save-repository
save-validator
snapshot-builder
snapshot-loader
migration
version-manager
save-format
errors
```

Cette séparation est pertinente.

Le gameplay ne doit pas connaître :

- `localStorage` ;
- IndexedDB ;
- une base distante ;
- un compte utilisateur ;
- l’API serveur.

Il doit uniquement produire et restaurer un état sérialisable.

---

# 2. Points forts de la fondation

## Séparation du domaine

La persistance est isolée du gameplay.

Cela permettra de remplacer progressivement :

```text
repository mémoire
```

par :

```text
repository navigateur
```

puis éventuellement :

```text
repository cloud
```

sans réécrire les systèmes métier.

---

## Sérialisation centralisée

La présence d’un serializer et d’un deserializer évite que chaque système produise son propre format de sauvegarde.

C’est essentiel pour garantir :

- la cohérence ;
- la validation ;
- la migration ;
- le débogage.

---

## Snapshots

Le système de snapshots permet théoriquement de capturer un état cohérent du jeu à un instant donné.

Il doit devenir la base de toute sauvegarde.

---

## Validation

Une sauvegarde chargée ne doit jamais être appliquée directement sans contrôle.

Le validateur doit vérifier :

- la structure ;
- les champs obligatoires ;
- la version ;
- les valeurs impossibles ;
- les identifiants inconnus ;
- les références supprimées.

---

## Migrations

La présence d’un système de migrations est une très bonne anticipation.

Albion Idle va continuellement modifier :

- les items ;
- les recettes ;
- les maîtrises ;
- les workers ;
- les zones ;
- les statistiques ;
- les structures de données.

Sans migration, chaque mise à jour risquerait de rendre les anciennes parties incompatibles.

---

# 3. Problème principal à confirmer

La fondation technique existe, mais une sauvegarde durable entre sessions n’est pas encore certifiée.

Un repository en mémoire peut suffire pour :

- les tests ;
- les prototypes ;
- les changements de scène ;
- un rechargement interne.

Il ne suffit pas pour :

```text
fermer complètement le navigateur
→ revenir plusieurs heures plus tard
→ retrouver sa progression
```

Work devra vérifier quelle implémentation de `SaveRepository` est réellement utilisée par le client.

---

# 4. Source autoritaire de la sauvegarde

Une sauvegarde ne doit pas être une copie brute de `GameBridgeState`.

Le bridge contient des view-models destinés à l’affichage.

La sauvegarde doit être construite à partir de l’état métier autoritaire.

---

## À sauvegarder

Selon la vertical slice, il faudra probablement conserver :

```text
identité et version de la partie
inventaire
banque
équipement
wallet
durabilité
progression
expérience
fame
maîtrises
zones débloquées
stage actuel
workers
affectations
tâches en cours
état du craft
état du raffinage
ressources
paramètres de progression hors-ligne
timestamp de dernière sauvegarde
```

---

## À ne pas sauvegarder directement

Les éléments suivants doivent généralement être reconstruits :

```text
sprites Phaser
objets React
listeners
event bus
services
registries
managers
textures
animations
view-models
fonctions
promesses
timers JavaScript bruts
```

---

## État temporaire à décider explicitement

Certains états nécessitent une règle produit :

```text
combat en cours
capacité en cours de cast
cooldowns
projectile actif
effet temporaire
gathering actif
craft en cours
worker en mission
boss partiellement blessé
```

Pour chaque cas, il faut décider si le chargement :

- reprend exactement ;
- recalcule depuis un timestamp ;
- annule proprement ;
- revient à un état stable précédent.

Ces décisions doivent être cohérentes avec l’AI_BIBLE.

---

# 5. Repository navigateur

## Recommandation

Pour la V1 locale, utiliser de préférence :

```text
IndexedDB
```

plutôt que `localStorage`.

---

## Raisons

IndexedDB convient mieux pour :

- des sauvegardes plus volumineuses ;
- des écritures structurées ;
- plusieurs slots éventuels ;
- des métadonnées ;
- des snapshots de secours ;
- des opérations asynchrones ;
- une évolution future.

---

## `localStorage`

`localStorage` peut fonctionner pour un prototype simple, mais présente plusieurs limites :

- stockage synchrone ;
- taille réduite ;
- absence de transactions avancées ;
- moins adapté aux snapshots multiples ;
- risque de blocage du thread principal.

---

## Interface cible

```ts
interface SaveRepository {
  save(slotId: string, data: SerializedSave): Promise<void>;
  load(slotId: string): Promise<SerializedSave | null>;
  delete(slotId: string): Promise<void>;
  list(): Promise<SaveMetadata[]>;
}
```

Le gameplay ne doit pas connaître l’implémentation concrète.

---

# 6. Stratégie de sauvegarde

## Sauvegarde manuelle

Un bouton peut exister pour rassurer le joueur, mais ne doit pas être le seul mécanisme.

---

## Sauvegarde automatique

Des sauvegardes doivent être déclenchées lors d’événements importants :

```text
craft terminé
équipement modifié
worker affecté
zone débloquée
progression importante
achat ou vente
réparation
récompense majeure
changement de paramètres
```

---

## Sauvegarde périodique

Une sauvegarde périodique peut compléter les sauvegardes événementielles.

Exemple :

```text
toutes les 30 à 60 secondes
```

La cadence exacte devra être choisie après mesure.

---

## Sauvegarde à la fermeture

Les événements navigateur peuvent être utilisés comme sécurité supplémentaire.

Ils ne doivent pas être considérés comme fiables à 100 %.

Le navigateur peut être fermé brutalement ou le processus interrompu.

---

## Déduplication

Plusieurs événements rapprochés ne doivent pas provoquer une écriture complète à chaque mutation.

Une stratégie de debounce ou de queue est recommandée.

---

# 7. Cohérence transactionnelle

Une sauvegarde doit représenter un état stable.

Exemple problématique :

```text
les ingrédients sont retirés
→ sauvegarde
→ le résultat du craft n’est pas encore ajouté
```

Après rechargement, les ressources seraient perdues.

---

## Règle

Les opérations suivantes doivent être atomiques du point de vue de la sauvegarde :

- craft ;
- raffinage ;
- achat ;
- vente ;
- réparation ;
- loot ;
- transfert inventaire/banque ;
- récompense de worker ;
- enchantement ;
- équipement.

La sauvegarde doit intervenir après validation complète de la transaction.

---

# 8. Version du format

Chaque sauvegarde doit contenir une version explicite.

Exemple :

```json
{
  "saveVersion": 3,
  "createdAt": "...",
  "updatedAt": "...",
  "gameVersion": "...",
  "payload": {}
}
```

---

## Différence entre versions

### `saveVersion`

Version de la structure de sauvegarde.

### `gameVersion`

Version du jeu ayant produit la sauvegarde.

### `contentVersion`

Version ou empreinte du contenu utilisé.

Ces trois informations peuvent devenir utiles pour diagnostiquer les incompatibilités.

---

# 9. Migrations

## Principe

Une sauvegarde ancienne ne doit jamais être modifiée directement sans passage par une migration contrôlée.

Exemple :

```text
v1
→ migration v1 vers v2
→ migration v2 vers v3
→ validation v3
→ chargement
```

---

## Une migration doit être

- déterministe ;
- testée ;
- sans dépendance à React ou Phaser ;
- capable de produire une erreur explicite ;
- idempotente lorsque c’est possible ;
- accompagnée d’une sauvegarde de secours.

---

## Cas à prévoir

- renommage d’un item ;
- suppression d’un item ;
- changement de profession ;
- changement de structure d’inventaire ;
- ajout d’un slot ;
- changement de courbe d’expérience ;
- fusion de monnaies ;
- modification des enchantements ;
- changement de format de worker ;
- suppression d’une zone.

---

# 10. Sauvegarde corrompue

Le client doit gérer une sauvegarde invalide sans écran blanc ni boucle de crash.

---

## Procédure recommandée

```text
1. Lire la sauvegarde
2. Vérifier l’intégrité
3. Migrer
4. Valider
5. Charger
```

En cas d’échec :

```text
1. Ne pas écraser immédiatement la sauvegarde
2. Conserver une copie de diagnostic
3. Tester le dernier snapshot valide
4. Informer clairement le joueur
5. Proposer une restauration
6. Ne réinitialiser qu’après confirmation
```

---

## Snapshots de secours

Conserver plusieurs versions récentes peut réduire le risque de perte totale.

Exemple :

```text
slot principal
backup n-1
backup n-2
```

Il ne faut pas multiplier les copies sans limite.

---

# 11. Progression hors-ligne

La progression hors-ligne est validée dans la vision du projet.

Elle doit être calculée à partir de données temporelles, pas en exécutant chaque tick manqué.

---

## Données nécessaires

```text
timestamp de dernière activité
activité active
worker en mission
craft ou raffinage en cours
rendements
limites maximales
état des ressources
règles de progression hors-ligne
```

---

## Calcul recommandé

```text
temps écoulé
→ bornage éventuel
→ calcul déterministe
→ génération d’un résultat
→ application transactionnelle
→ écran récapitulatif
→ sauvegarde
```

---

## Points à décider

- durée maximale hors-ligne ;
- rendement à 100 % ou réduit ;
- activités autorisées hors-ligne ;
- combats simulés ou arrêtés ;
- gestion de la mort ;
- worker continuant sa mission ;
- capacité de stockage ;
- ressources perdues lorsque la banque est pleine ;
- ordre de résolution de plusieurs activités.

---

## Risques

- gains dupliqués après plusieurs rechargements ;
- modification de l’horloge système ;
- timestamp futur ;
- calcul très lourd ;
- incohérence entre client et future sauvegarde cloud ;
- récompense appliquée avant sauvegarde.

---

## Protection minimale

La V1 locale peut vérifier :

- timestamp invalide ;
- temps négatif ;
- durée anormalement longue ;
- double application d’un même intervalle.

La lutte avancée contre la triche ne doit pas être prioritaire pour une V1 solo.

---

# 12. Authentification

## État

L’AI_BIBLE prévoit un système d’authentification, mais son implémentation complète ne doit pas précéder la stabilisation de la sauvegarde locale.

---

## Ordre obligatoire

```text
1. Format de sauvegarde stable
2. Repository local durable
3. Migrations
4. Reprise hors-ligne
5. Contrats cloud save
6. Authentification
7. Synchronisation local/cloud
```

---

## Pourquoi

L’authentification identifie le joueur.

Elle ne résout pas à elle seule :

- le format de sauvegarde ;
- les migrations ;
- les conflits ;
- les données corrompues ;
- les changements de version.

Commencer par l’authentification risquerait d’ajouter un backend sans résoudre le vrai problème.

---

# 13. Cloud save

## Architecture cible

```text
Gameplay Runtime
        │
        ▼
SaveManager
        │
        ▼
SaveRepository
   ┌────┴─────┐
   ▼          ▼
Local      Cloud
```

Le runtime ne doit pas savoir si la sauvegarde est locale ou distante.

---

## Synchronisation

Une stratégie de synchronisation devra être choisie.

Cas possibles :

```text
local plus récent
cloud plus récent
même version
conflit
première connexion
appareil hors-ligne
suppression locale
migration nécessaire
```

---

## Mauvaise stratégie

```text
la dernière écriture gagne toujours
```

Cette règle peut écraser plusieurs heures de progression.

---

## Stratégie recommandée

Comparer au minimum :

- version de la sauvegarde ;
- date de modification ;
- identifiant de révision ;
- progression significative ;
- origine de la sauvegarde.

En cas de conflit non résoluble automatiquement, présenter un choix clair au joueur.

---

# 14. Backend

## Rôle futur

Le serveur Fastify pourra fournir :

- création de compte ;
- connexion ;
- session ;
- lecture et écriture de cloud save ;
- validation de version ;
- métadonnées ;
- éventuellement télémétrie.

---

## Ce qu’il ne doit pas faire immédiatement

- simuler tout le gameplay ;
- devenir autoritaire sur chaque tick ;
- reproduire le moteur complet ;
- gérer des classements avant stabilisation du jeu ;
- complexifier la vertical slice.

Albion Idle reste actuellement un jeu principalement local.

---

# 15. Sécurité

## Secrets

Aucun secret ne doit être stocké dans :

- le dépôt GitHub ;
- le client Vite ;
- les fichiers JSON publics ;
- les variables commençant par `VITE_` lorsqu’elles sont réellement secrètes.

---

## Données client

Toute donnée envoyée par le client doit être considérée comme modifiable.

Pour une première V1 solo, cela est acceptable.

Pour de futurs classements ou échanges entre joueurs, le serveur devra valider les données importantes.

---

## Priorité

La sécurité avancée n’est pas prioritaire tant qu’aucune économie multijoueur ou compétition publique n’existe.

# 17. Critères d’acceptation V1

Le système de sauvegarde sera considéré comme fonctionnel lorsque :

- le joueur peut fermer entièrement le navigateur ;
- la progression est retrouvée au redémarrage ;
- aucun objet n’est dupliqué ;
- aucun objet n’est perdu lors d’une transaction terminée ;
- les workers reprennent dans un état cohérent ;
- les zones et maîtrises sont restaurées ;
- une sauvegarde ancienne peut être migrée ;
- une sauvegarde invalide ne fait pas planter le jeu ;
- la progression hors-ligne n’est appliquée qu’une fois ;
- les erreurs sont visibles et récupérables ;
- les tests automatisés couvrent les chemins critiques.

# 20. Conclusion

Albion Idle possède déjà une fondation de persistance plus avancée qu’un prototype classique.

Cependant, la présence d’un package de sauvegarde ne suffit pas à garantir la continuité réelle d’une partie.

La prochaine étape n’est pas l’authentification.

La prochaine étape est de certifier le parcours suivant :

```text
jouer
→ progresser
→ sauvegarder
→ fermer le navigateur
→ revenir
→ migrer si nécessaire
→ appliquer l’absence
→ reprendre sans perte
```

Une fois ce parcours fiable, la sauvegarde cloud et l’authentification pourront être ajoutées sans remettre en cause le gameplay.
````

````markdown
# PARTIE 9 — DETTE TECHNIQUE, RISQUES ET PRIORITÉS

---

# Objectif

Cette partie transforme les constats précédents en un plan de risque exploitable.

Elle distingue :

- les problèmes qui bloquent directement le développement ;
- les dettes qui ralentiront rapidement Work ;
- les sujets nécessaires avant une vraie V1 ;
- les optimisations pouvant attendre.

La classification utilisée est :

```text
P0 = bloquant immédiat
P1 = consolidation prioritaire
P2 = nécessaire avant V1
P3 = optimisation ou polish
```

# 1. Vue d’ensemble

La dette technique d’Albion Idle n’est pas répartie uniformément.

Elle est surtout concentrée dans :

```text
apps/client/src/state/GameContext.tsx
apps/client/src/game/GameBridge.ts
apps/client/src/state/bridgeSync.ts
scripts de build du monorepo
configuration Vercel
sources de données dupliquées
persistance navigateur non certifiée
documentation obsolète
```

À l’inverse, les packages suivants semblent structurellement sains :

```text
packages/core
packages/data
packages/gameplay
packages/persistence
packages/shared
packages/tooling
```

Le risque principal n’est donc pas une mauvaise architecture globale.

Le risque est une **mauvaise intégration progressive au niveau du client**.

# 2. P0 — Bloquants immédiats

---

## P0.1 — Pipeline de build non totalement standardisé

### Constat

Le build de production a nécessité :

- la construction explicite des packages internes ;
- un alias Vite supplémentaire pour `@game/persistence` ;
- le lancement direct de `vite build` ;
- le contournement temporaire du typecheck client.

### Risque

Le projet peut :

- fonctionner en local ;
- se déployer sur Vercel ;
- tout en conservant des erreurs TypeScript non résolues.

### Impact

Très élevé.

Cela permettrait à des régressions de s’accumuler sans être bloquées par la CI.

### Action

Créer une commande canonique unique.

Exemple cible :

```bash
pnpm build
```

Cette commande doit :

1. construire les packages dans le bon ordre ;
2. typechecker le client ;
3. générer `apps/client/dist` ;
4. fonctionner en local ;
5. fonctionner en CI ;
6. fonctionner sur Vercel.

### Critère de sortie

```text
pnpm build
```

passe depuis un clone propre.

---

## P0.2 — Typecheck client non totalement sain

### Constat

Des erreurs ont déjà été observées :

- paramètres implicitement `any` ;
- types de professions désalignés ;
- famille `gloves` absente ;
- imports workspace non résolus dans certaines conditions.

### Risque

Les types ne garantissent plus la cohérence entre :

```text
gameplay
bridge
React
Phaser
données
```

### Impact

Très élevé.

Le projet repose fortement sur TypeScript pour maintenir ses nombreux domaines.

### Action

Corriger toutes les erreurs sans :

- `@ts-ignore` ;
- `any` généralisé ;
- `skipLibCheck` utilisé pour masquer le problème ;
- désactivation de règles strictes.

### Critère de sortie

```bash
pnpm typecheck
```

passe sans erreur.

---

## P0.3 — CI GitHub à certifier

### Constat

La CI est bien conçue sur le papier.

Elle exécute :

```text
lint
typecheck
tests
build
validation data
validation assets
```

### Risque

Si les scripts locaux ne sont pas sains, la CI peut être :

- rouge ;
- ignorée ;
- contournée ;
- différente du pipeline Vercel.

### Impact

Très élevé.

Une CI non fiable ne protège plus `main`.

### Action

Rendre la CI identique au pipeline local.

### Critère de sortie

La branche `main` est verte sur toutes les étapes.

---

## P0.4 — Versions Node et PNPM désalignées

### Constat

Le dépôt déclare :

```json
"packageManager": "pnpm@9.15.0"
```

alors que Vercel a détecté un lockfile généré par PNPM 10.

Node est déclaré avec :

```json
"node": ">=22"
```

### Risque

- différences entre local, CI et Vercel ;
- mise à jour automatique vers une future version majeure ;
- lockfile non reproductible ;
- bugs difficiles à reproduire.

### Action

Aligner :

```text
Node 22.x
PNPM version unique
Corepack
lockfile
CI
documentation
```

### Critère de sortie

Toutes les machines utilisent les mêmes versions.

# 3. P1 — Consolidation prioritaire

---

## P1.1 — `GameContext.tsx` monolithique

### Constat

Le fichier dépasse plusieurs milliers de lignes.

Il semble coordonner presque tous les domaines du jeu.

### Risque

Chaque nouvelle feature augmente :

- le temps de lecture ;
- le contexte Work ;
- la probabilité de régression ;
- les dépendances croisées ;
- les erreurs de typage ;
- la difficulté des tests.

### Impact

Élevé et croissant.

### Action

Créer progressivement :

```text
GameClientRuntime
CombatRuntimeModule
ProgressionRuntimeModule
EconomyRuntimeModule
ProductionRuntimeModule
WorkerRuntimeModule
PersistenceRuntimeModule
```

### Critère de sortie

`GameContext` devient une façade React.

---

## P1.2 — `GameBridge.ts` trop large

### Constat

Le bridge agrège de nombreux domaines.

Il contient également des types UI et des valeurs par défaut.

### Risque

Il peut devenir un second monolithe.

### Action

Découper en slices de domaine.

Exemple :

```text
combat
inventory
production
workers
world
progression
```

### Critère de sortie

Chaque slice peut être testée indépendamment.

---

## P1.3 — Mappings manuels dans `bridgeSync.ts`

### Constat

Les conversions gameplay → UI sont nombreuses.

### Risque

- oubli d’une nouvelle valeur ;
- type drift ;
- fallback silencieux ;
- logique métier dans les mappers ;
- erreurs `any`.

### Action

Créer des mappers :

- purs ;
- exhaustifs ;
- séparés par domaine ;
- testés.

### Critère de sortie

Une nouvelle valeur gameplay provoque une erreur de compilation si elle n’est pas mappée.

---

## P1.4 — Doubles sources de vérité

### Constat

Les données peuvent être réparties entre :

```text
content/data
apps/client/src/data
GameContext
packages/gameplay
GameBridge defaults
```

### Risque

Deux versions différentes d’une même recette, arme ou courbe de progression.

### Impact

Élevé.

### Action

Définir une source canonique par famille.

### Critère de sortie

Ajouter un contenu ne nécessite pas plusieurs modifications parallèles.

---

## P1.5 — Sauvegarde durable non certifiée

### Constat

Le package persistence existe, mais la reprise navigateur complète n’est pas prouvée.

### Risque

Perte de progression.

### Impact

Critique pour un idle game.

### Action

Implémenter et tester un repository navigateur durable.

### Critère de sortie

Fermeture complète puis reprise sans perte.

---

## P1.6 — Vertical slice non certifiée de bout en bout

### Constat

De nombreux systèmes existent.

Il n’existe pas encore de preuve consolidée qu’ils fonctionnent ensemble.

### Risque

Le dépôt semble très avancé, mais l’expérience joueur peut rester fragmentée.

### Action

Certifier la boucle :

```text

→ loot
→ gathering
→ refining
→ craft
→ équipement
→ progression
→ sauvegarde

### Critère de sortie

Un joueur externe termine la boucle sans intervention.

## P1.7 — Documentation obsolète

### Constat

Le README indique encore une phase très ancienne du projet.

### Risque

Mettre à jour :

La documentation reflète uniquement l’état vérifié.
````

# Définition d'une mission réussie

Une mission est réussie uniquement si :

- le comportement attendu fonctionne ;
- aucun comportement existant n'est cassé ;
- le build est vert ;
- les tests sont verts ;
- le code est plus simple qu'avant.

Si une fonctionnalité fonctionne mais augmente fortement la dette technique :

la mission est considérée comme incomplète.

# Règle d'or

À partir de maintenant, chaque intervention Work doit respecter la maxime suivante :

> **"Étendre l'architecture existante avant de créer une nouvelle architecture."**

C'est cette discipline qui permettra à Albion Idle de rester maintenable malgré sa croissance.

# CONCLUSION GÉNÉRALE DE L'AUDIT

À l'issue de cet audit, le constat est clair :

- Les fondations techniques sont solides.
- L'architecture est suffisamment mature pour supporter plusieurs années de développement.
- La priorité n'est plus d'ajouter des systèmes, mais de stabiliser, certifier et exploiter ceux déjà présents.
- Le prochain objectif n'est pas une nouvelle fonctionnalité majeure, mais une **Vertical Slice complète, stable et testée**, servant de référence pour toute la suite du projet.

Ce document constitue désormais la feuille de route technique officielle du projet Albion Idle.
