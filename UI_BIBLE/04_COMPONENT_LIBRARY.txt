# UI_BIBLE/04_COMPONENT_LIBRARY.md

# Albion Idle — Component Library

Version: 1.1
Status: VALIDATED
Last update: 2026-08-22

---

# Purpose

The Component Library defines every reusable UI element.

Every screen in Albion Idle must be built using these components.

Creating new components should remain exceptional.

---

# Philosophy

Build once.

Reuse everywhere.

Consistency has priority over uniqueness.

---

# Core Components

## Panel

Primary container.

Used for:

- Right Panel
- Dashboard
- Settings
- Character
- Inventory
- Craft
- World
- Island

---

## Card

Primary information container.

Cards group related information.

Every panel is composed of Cards.

Cards share:

- spacing
- borders
- typography
- shadows

---

## Button

Shared button component.

States:

- Default
- Hover
- Active
- Disabled

Buttons always follow the Design System.

---

## Progress Bar

Shared component.

Used for:

- HP
- Masteries
- Crafting
- Refining
- Gathering
- Workers
- Zone Progression
- Research
- Expeditions

Progress Bars always share the same visual language.

---

## Item Slot

Reusable slot component.

Supports:

- equipment
- inventory
- bank
- crafting
- rewards

---

## Badge

Small visual indicator.

Examples:

- NEW
- RARE
- T8
- +3
- COMPLETE

---

## Tooltip

Provides contextual detailed information.

Appears on hover/focus and disappears automatically.

A Tooltip must explain useful context, not simply repeat the visible label.

The base interface must remain understandable without the Tooltip.

Item Tooltips read item/equipment gameplay definitions as their source of truth. Missing or pending visual assets must never suppress authored stats, effects, tier or other item information.

For dense action lists, prefer attaching explanatory Tooltips to the relevant action control rather than making the entire row/card a hover target when doing so would hurt readability.

Tooltip behavior/positioning should be shared rather than recreated per module.

---

## Tabs

Used to switch between sections inside the same panel.

Tabs never replace the Game World.

---

## Search Bar

Shared search component.

Supports:

- Inventory
- Bank
- Craft
- Marketplace

---

## Dropdown

Shared selection/filtering component.

Supports:

- sorting
- categories
- families
- recipes
- rarity
- tiers

When an operating-system-native popup is visually inconsistent or unreadable inside the game panel, use the shared game-styled dropdown presentation.

A game-styled Dropdown must provide:

- opaque surface/background;
- sufficient text contrast;
- clearly visible selected state;
- distinct hover and keyboard-focus states;
- readable option spacing;
- vertical scrolling for long option sets;
- no horizontal scrolling;
- correct overlay/z-index above the surrounding panel;
- keyboard accessible selection;
- data-driven option order supplied by the owning presentation model.

The Dropdown must not invent sorting, filtering or gameplay relationships. It renders the options and order supplied by its model.

---

## Toggle

Shared ON/OFF component.

Used for:

- filters
- settings
- automation

---

## Timer

Displays remaining duration.

Examples:

- Craft
- Workers
- Island
- Research
- Expeditions
- Buffs

---

## List

Shared vertical list.

Supports:

- objectives
- quests
- recipes
- workers
- notifications

---

## Grid

Shared grid layout.

Used for:

- inventory
- bank
- crafting recipes
- collections

---

## Modal

Exceptional component.

Reserved for:

- confirmations
- warnings
- purchases
- destructive actions

Modals should never replace normal navigation.

---

# Scroll Behavior

Vertical scrolling is preferred.

Horizontal scrolling should be avoided.

Pagination should only be used when absolutely necessary.

---

# Empty States

Every component must define an Empty State.

Example:

"No active craft."

instead of

Empty panel.

---

# Loading States

Every component supports:

- Loading
- Success
- Error
- Empty

---

# Error States

Errors should explain:

- what happened
- why
- how to resolve it

---

# Reusability Rules

MUST

- Reuse existing components.
- Maintain identical spacing.
- Maintain identical typography.
- Maintain identical interaction patterns.
- Keep reusable presentation components free of gameplay-specific branching.

MUST NOT

- Create duplicate components.
- Introduce isolated visual styles.
- Duplicate existing functionality.
- Hide gameplay data because a final visual asset does not yet exist.

---

# Future Compatibility

Every new feature introduced in Albion Idle must first determine whether an existing component can be reused.

New components should only be created when no existing component can satisfy the requirement.
